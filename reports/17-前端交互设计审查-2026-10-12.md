## 1. 问题清单（按心理学机制归类）

### A 类 · 反馈与时延 —— 「等待感知」失控

#### 🔴 A1 [P0] 任务进行中没有任何进度指示

**实测确认**：`grep Progressbar|spinner|indeterminate` 在 `forge-gui/**/*.py` **零命中**；工作台无任何耗时展示。

当前唯一的"进度"是一行文本 `task_label`，而它被两种语义争用：

- `send()` 置为 `'Agent · 正在执行真实任务'`（`app.py:722`）
- 紧接着 `handle_event` 用**原始事件类型**覆盖它：`'Agent · ' + kind + ' · ' + str(data.get('tool', data.get('phase','')))`（`app.py:777`）

于是用户实际看到的是 `Agent · tool_call · write_file`、`Agent · workflow_state · executing` 这类**开发者词汇**在闪。

**心理代价**：模型请求阶段（通常数十秒）没有任何变化 → 用户进入"未知等待"。人因研究反复证实，*indeterminate* 等待若无反馈，主观时长会被显著放大；且无参照时会触发"是不是卡死了"的怀疑，进而重复点击（而 `send` 有 busy 保护，重复点击只得到"请等待"的挫败感）。

**修复方向**：
1. 进入不确定阶段（等模型返回）时，`task_label` 改为**稳定状态文案 + 不定量指示**（脉冲圆点/呼吸动画），**不要**用事件类型填充；
2. 增加已用时间（`time.monotonic()`，每 1s 刷新一次即可，成本极低）；
3. 事件类进度（工具开始/结束）走独立区域，不与"存活信号"混用。

#### 🔴 A2 [P0] 事件密集期 UI 全量重建，交互抖动

两个叠加的热点，都位于**每个事件都会走到**的路径上：

- `render_evidence()` 每次 `delete('1.0','end')` 后**整块重插**全部文本（`app.py:755-758`），由 `handle_event` 对 15 类事件**无条件触发**（`app.py:768-771`）；
- `handle_event` 对每个 `tool_call` 调用 `refresh_project()`（`app.py:796`）→ 触发工作区扫描线程。

一个 40 步的编码任务会产生数百个事件，即数百次整块文本重建 + 数百次目录扫描。同时 `_drain` 以 40ms 轮询、12ms 预算与之竞争（`app.py:284-306`）。

**用户可感后果**：执行期间滚动卡顿、选中文本被清空（`render_evidence` 会删掉用户正在选中的内容）、输入框响应变慢。

**修复方向**：
1. `render_evidence` 改**增量**：为 plan/actions/agents/tests 各维护一个行号锚点，只 `insert` 新行；
2. 工具事件刷新项目树改为**节流**（如 800ms 合并一次，复用已有的 `_scan_busy/_scan_pending` 模式）；
3. 重绘前保存并恢复 `workflow` 的 `see()` 与选区。

### B 类 · 认知负荷 —— 超出工作记忆的控件密度

#### 🔴 B1 [P0] Agent 栏 420px 宽度内堆叠 7 组控件

`_build_agent`（`app.py:190-244`）自上而下：

```
task_label → 3 个日志 tab → context_label → 输入框 →
[模型下拉 + 发送] → [规划 + 权限 + 复审 + 恢复] →
[子Agent + 取消 + 测试 + 独立模型] → [任务角色 + 模型回显]
```

**心理代价**：单屏同时呈现 14 个可交互元素，远超"7±2"的并行处理上限；用户必须逐行扫描才能定位目标。更糟的是**语义相近的控件被分散在不同行**（模型相关控件出现在 4 处：header 的"模型角色"`app.py:85`、本栏模型下拉 `213`、本栏"独立模型"`236`、主 GUI 的 Agents 页），每次都要重新建立"这次该点哪个"的判断。

#### 🟠 B2 [P1] 三个日志 tab 内容重叠，调试信息被提到同一层级

`app.py:193-203`：对话 / 任务·子Agent / 完整事件。其中"完整事件"直接 `json.dumps(..., indent=2)` 追加（`app.py:772-775`），是**开发者调试通道**，却与用户对话、任务进度并列为三个一等 tab。

**建议**：默认只保留"对话 + 任务"两个 tab；"完整事件"下沉为开发者开关（如 `--dev-events` 或设置项），默认隐藏。

#### 🟠 B3 [P1] 输出区 20% 高度塞 5 个 tab，且与项目栏重复

`app.py:172-176`：tabs 权重 4、output 权重 1，output 内含 Diff/终端/测试/问题/输出。而"Diff"与项目栏的"Git 变更"页（`app.py:122-145`）功能重叠。

**心理代价**：5 个 tab 挤在约 20% 高度里，标签被截断的概率高，用户需要点击-切换-猜测。且 20% 对"终端/测试"这类需要阅读输出的视图过矮。

#### 🟠 B4 [P1] 前置 chrome 四层才见到内容

`app.py:77-110`：header（标题+模式+IDE 开关+模型角色）→ options（打开项目+近期项目+预设+专注+路径提示）→ panes → status。**四个水平条**之后才是工作区。首屏信息密度被非内容元素占据。

其中"专注：编辑器 / Agent"按钮（`app.py:95`）与预设下拉的 `focus` 值（`app.py:92`）语义重叠——两个入口做同一件事，用户无法判断差异。

### C 类 · 设计系统一致性 —— 建了没用上

#### 🟠 C1 [P1] 工作台绕开字体刻度，硬编码 4 处

设计系统已定义完整刻度：`FONT_TITLE(15 bold) / FONT_SECTION(12 bold) / FONT_UI(11) / FONT_SMALL(10)`（`gui_theme.py:154-159`）。

但 `app.py` 硬编码：

```python
79:  font=('Segoe UI', 13, 'bold')   # 标题，应为 FONT_TITLE
115: font=('Segoe UI', 11, 'bold')   # 区块标题，应为 FONT_SECTION
207: font=('Segoe UI', 11)           # 输入框，应为 FONT_UI
247: font=('Segoe UI', 11)           # 只读文本，应为 FONT_UI
```

整个 `app.py` 只用了 3 次 `FONT_*` token（`FONT_MONO_SM` 等）。**后果**：改一次全局字号刻度，工作台不会跟着变；且 13/11 混用使层级关系模糊（13 既不是 15 也不是 12，读起来像"差一点"）。

#### 🟠 C2 [P1] 建了完整的矢量图标系统，导航却在用 emoji

`ui_icons.py` 是一套**与字体无关**的图标体系：24×24 网格、统一 1.7px 圆角描边、`draw_icon`/`IconCanvas`/`icon_image`/`IconButton`/图集 tile（`ui_icons.py:15-131,325`）。

但主导航用的是 emoji（`forge_gui_v2.py` `NAV_ITEMS`）：

```python
("chat", "对话", "💬"), ("task", "任务", "✅"), ("schedules", "定时任务", "⏰"),
("agents", "Agents", "🤖"), ("development", "开发", "🛠"), ...
```

**代价**：
- emoji 依赖系统 emoji 字体，跨平台字形与色彩不可控（这也是 `gui_theme.py:316-353` 要专门做 `is_emoji()`/`emoji_font()` 分流的原因）；
- 彩色 emoji 与"克制、低饱和"的调色板（`gui_theme.py:92-97` 的设计意图）**气质冲突**，专业工具感被削弱；
- 已经画好的线性图标资产闲置。

#### 🟡 C3 [P2] Agent 进度有结构化数据，却渲染成扁平文本行

`render_evidence`（`app.py:742-744`）：

```python
lines.extend(f"{row['agent']} · {row['status']} · {row['run_id'][:8]} · {row.get('model','')}"
             for row in view.agents.values())
```

而 `TaskEvidence` 早已采集 `depth`（`evidence.py:34-41`）、`usage/tokens`（`evidence.py:42-45`）、`checkpoints`（`evidence.py:90-91`）——**这些数据一个都没进 UI**。

**心理代价**：父子 Agent 关系不可见，用户无法回答"现在是谁在干活、谁等谁"。用 run_id 前 8 位十六进制做标识，对人类记忆极不友好。

#### 🟡 C4 [P2] 搜索框提示放在下方，白占一行

`app.py:118-121`：Entry 下方再放一个 `Label('文件名搜索 · Enter')`。既占垂直空间，又把"按回车提交"这个本可用 placeholder 或 `<Return>` 即时反馈解决的负担转给用户。

### D 类 · 状态可见性与安全感的交互表达

#### 🔴 D1 [P0] 权限开关与"规划深度"同权重，且无持久状态标识

`app.py:222-225`：

```python
ttk.Combobox(row2, textvariable=self.planning, values=['none','low','medium','high'], ...).pack(side='left')
perms = ttk.Combobox(row2, textvariable=self.permission, values=['read-only','workspace-write'], ...)
```

**规划深度**（影响成本与耗时）与**写权限**（影响能否改你磁盘上的文件）视觉权重完全相同。后者是安全边界，应当：
- 与前者在视觉上分层（如分组、标签、或不同控件形态）；
- **常驻显示当前权限**——目前只在 git 刷新时短暂出现在 status（`app.py:440`），任务运行中、用户最需要确认"我现在是什么权限"时反而看不到。

> 已有补救：升级有确认框且文案准确（`app.py:690-696`，见 ✅4）。问题在**状态可见性**，不在**授权流程**。

#### 🟠 D2 [P1] 阻塞性条件只写状态栏，不弹窗不引导

`app.py:325-327`：有未保存标签时切换项目，仅在底部 status 写一行"请先保存或关闭未保存标签，再切换项目"。

**心理代价**：状态栏是**易失**的（下一条消息即覆盖），用户很可能根本没看到，然后困惑"为什么点了没反应"。**会阻断用户流程的条件，必须用模态或内联阻塞提示，不能只写状态栏。**

#### 🟡 D3 [P2] 最好的提示被放在最弱的通道

`app.py:883`：恢复会话后提示"已恢复真实对话；未知操作不重放。请输入检查或继续任务。"——这句话对建立信任极其重要，却只出现在状态栏，几秒后消失。

**建议**：这类"系统为你做了什么、没做什么"的关键说明，应以内联横幅/卡片形式停留，直到用户主动关闭。

### E 类 · 键盘与专家效率

#### 🟠 E1 [P1] 发送快捷键非惯例，且输入区无任何键位提示

`app.py:210`：`<Control-Return>` 发送。主流聊天/IDE 是 Enter 发送、Shift+Enter 换行（或反之并在输入框旁明示）。

当前唯一键位提示在编辑器区（`app.py:165` 提到 Ctrl+S），**输入框附近没有任何提示**——用户要靠试。

#### 🟡 E2 [P2] 无快捷键发现入口

工具已有相当多高频操作（发送、取消、保存、刷新、切换 tab、切项目），但无 `?` 面板或菜单陈列。

## 3. 界面方案：Agent 栏重组

核心思路：**把"每次都用"和"偶尔才用"分开**，让首屏只剩 3 个决策点。

```
┌─ Agent ───────────────────────────────┐  ← task_label：状态 + 权限徽标 + 已用时间
│ ● 执行中 · workspace-write · 00:42     │     （权限常驻，修 D1）
├───────────────────────────────────────┤
│ [对话] [任务 ▸ 2 个子 Agent]           │  ← 只 2 个 tab（修 B2）
│  …消息流…                              │
├───────────────────────────────────────┤
│ ┌─────────────────────────┐  ┌──────┐ │
│ │ 输入任务…          Enter │  │ 发送 │ │  ← 主操作放大（Fitts）
│ └─────────────────────────┘  └──────┘ │
│ ⌥ 已附加 2 个文件 · 点击管理           │  ← context_label 变为可交互摘要
├───────────────────────────────────────┤
│ ▸ 高级设置（模型 / 角色 / 规划 / 子Agent）│  ← 折叠，默认收起（修 B1）
└───────────────────────────────────────┘
```

**关键变化**
1. **权限从下拉变成徽标**：常驻可见，点击才展开切换（切换仍走现有确认框）。
2. **发送按钮独立成主按钮**：不再与 24 宽的模型下拉挤在同一行。
3. **模型/角色/规划/子Agent/测试/复审 全部下沉折叠区**：这些是"配置一次，跑多次"的参数，不是每次任务的决策。
4. **上下文附件变成可管理的摘要行**：现在是纯文本"未附加编辑器内容"（`app.py:205`）。

### 任务 tab 内部：用树替代扁平文本

```
▾ forge · 执行中 · 12.4k tok · 预算 3/16
  ├─ tester   · 完成   · 41s · 3.1k tok
  └─ reviewer · 运行中 · 12s · 1.8k tok

  ☑ 读取相关代码

工具（最近 100 条，共 137 条）        ← 补上总数，别让用户猜截断
  ✓ write_file  src/x.py
  ✗ shell_exec  pytest tests/   → 查看输出
```

数据源全部已存在：`evidence.py:34-45` 的 `depth/usage`、`app.py:743` 已有 model、`app.py:745` 已在文案里写"最近 100 条"但没给总数。

## 4. 设计系统治理建议

1. **立一条硬规矩**：`forge-gui/` 内新增 UI 代码禁止硬编码 `font=(...)`，一律用 `gui_theme.FONT_*`；可加一个极简的静态检查脚本（扫 `font=('Segoe UI'` 字面量）挂进 CI。
2. **图标统一入口**：`NAV_ITEMS` 的第三列从 emoji 改为 `ui_icons` 键名，由渲染层统一走 `icon_image()`。保留 emoji 仅用于消息正文内的表情（那里彩色是合理的）。
3. **把"设计意图注释"当作规范传递**：`gui_theme.py:92-97` 的写法值得推广——每个非显而易见的取值都写清"为什么"。建议在 `decor.py`/`brand_marks.py` 补同类注释。
4. **状态色不挪用**：`gui_theme.py:67` 已注明 `brand_ice` 仅用于品牌图形、避免混同状态颜色——这条纪律要继续守，尤其是新增"执行中"状态色时，不要直接拿 `accent` 或 `info` 复用。

## 5. 验收标准

### 交互性能（可量化）

| 指标 | 现状 | 目标 |

## 附：一句话总结

**这个 UI 的底子比表象好**——线程编组、诚实文案、调色板都是认真做的；问题集中在**"运行时反馈"和"信息密度"**两处：任务跑起来后用户得不到存活信号（无进度指示、状态栏被事件类型占据），以及 Agent 栏把 14 个控件塞进 420px。修 P0 五项不需要动架构，主要是把已有的 `depth`/`usage` 数据真正渲染出来、把 `render_evidence` 从全量重绘改增量、把权限做成常驻徽标。
