# 后端上下文与缓存骨架集成 · 2026-11-04

基于已核验的天枢 4.0.2 发布包行为，按 Forge 的 Python 内核重新实现必要机制；没有装入上游混淆 JavaScript，也没有替换本地验证过的厂家适配表。

## 已进入实际调用链

| 模块 | 职责与调用入口 |
| --- | --- |
| `forge/route_capabilities.py` | 当前部署的能力交集、完整请求估算、输出预留和发送前校验；由 Provider、主循环、直连及网关共用。 |
| `forge/context_transaction.py` | 压缩前归档、源状态摘要校验、候选历史检查和来源检查点；由 Agent 主循环调用。 |
| `forge/cache_metrics.py` | 压缩版本与重建请求标记、明确分母的缓存统计；由主循环和统一结果协议调用。 |

原来的 `model_kind_id` 继续决定型号身份和适配器。新增能力声明属于具体路由和实际 wire model ID，不改写型号身份，不以供应商名称猜测部署容量。

## 缓存兼容边界

- 未声明新能力时，原请求内容、缓存标记策略、缓存键和路由选择保持原逻辑。事务编号、检查点、能力元数据均留在宿主侧报告，不加入提示词。
- 仍按原压缩策略决定是否整理历史。只有明确声明的 `contextWindow` 会增加容量触发条件；没有从天枢照搬 0.60/0.85 的整理比例，也没有引入额外摘要模型调用。
- 成功压缩确实会改写历史，旧历史的缓存不能保证继续命中。首个使用新历史版本的请求标记 `cache_rebuild`；之后继续执行“已发送前缀只追加”。MoA/premium 的独立集成提示不标成历史重建。
- 原始 usage、成本累计、既有逐请求命中率及平均值继续保留。新指标不会覆盖旧指标。

`usage.cache_trajectory.coverage` 的新字段：

| 字段 | 分母与范围 |
| --- | --- |
| `all_observed` | 有有效输入和缓存回执的全部请求；以输入 token 加权，而非平均请求比例。 |
| `rebuild` | 上述集合中，压缩后首次使用该版本历史的请求。 |
| `non_rebuild` | 上述集合排除重建请求；仍可能含冷启动、规划或独立集成请求，不能直接称作“稳态命中率”。 |
| `eligible_prefix` | 仅对显式声明 `cacheTailRule` 的请求，按规则扣除估算结构性尾部；单独列出排除的 token。 |
| `unknown_requests` / `invalid_requests` | 缺失或无效观测的请求数；缺失缓存字段不冒充已观测到的零命中。 |
| `duplicate_observations` | 有明确请求及尝试 ID、且在同一 provider/model 下重复的观测；不据此改写计费总账。 |

`deepseek-128` 仅为可选的结构性尾部估算规则，不按 DeepSeek 名称自动启用。已有 362 输入 / 128 缓存的回执，全部输入口径仍为 35.36%；启用该估算后前缀口径为 100%。两者是同一回执的不同分母，不代表收益提升。

## 压缩事务

1. 对当前消息和宿主策略做摘要。包含路由身份、端点/账号指纹、能力、预算、工具声明、会话和运行身份。
2. 原消息通过既有秘密保护后，保存到 `<Forge home>/context-archives/ctx-<事务编号>.json`。先写 `.pending` 文件并 fsync，成功后更名；不完整文件不会成为有效归档。
3. 在消息副本上运行已有确定性摘要，保留 system/developer、被钉住的当前任务和完整原生工具调用/结果组。
4. 仅当候选确实缩小、保护消息未变、工具配对完整、已知容量估算通过、源状态未变且没有取消时提交。
5. 事件记录前后大小、摘要、归档引用和来源覆盖区间。检查点标记 `unverified_excerpt`，不把摘要推断升级成已验证事实。

软策略整理失败时，继续使用当前原历史；已声明的容量仍不满足时，以 `context_limit` 停止，不发送超预算候选。`context.mode=lossless` 在后端真正禁止压缩，容量不足直接停止；该模式也传给子运行。归档不自动删除，便于排错与后续恢复工具使用。

## 可选部署配置

以下是 provider 行的配置片段，数字只演示语法，**不是任何型号的容量规格**。正式填写应使用该实际部署的可信规格或验证证据。

```json
{
  "modelKinds": {"deployment_name": "deepseek.v4.flash"},
  "routeCapabilities": {
    "contextWindow": 64000,
    "maxOutputTokens": 4096,
    "tools": true,
    "stream": true
  },
  "modelCapabilities": {
    "deployment_name": {
      "contextWindow": 32000,
      "reasoningEfforts": ["low", "high"]
    }
  }
}
```

还支持 `vision` 和 `cacheTailRule`（`none` / `deepseek-128`）。未知字段、错误类型和无效规则提前报错。全路由与具体部署的数值取较小值、布尔能力取交集、effort 列表取交集；具体部署不能放宽路由限制。未声明的能力保持未知，不凭空判定支持或不支持。

默认输出预算可以按明确上限收窄；用户显式输出预算超限则报错。即使 `adapt=false`，明确声明的路由约束仍生效。网关在别名映射后按实际 wire ID 查询能力；fallback 也会在最终发送前独立检查，不为躲过约束自动换到其他收费路由。

估算覆盖消息、system、工具声明、工具调用参数及协议余量，并预留输出空间。它使用序列化字符估算，不是厂家 tokenizer，图像 token 尤其不能据此精确计算。主循环预检查首选路由，实际发送前再校验最终整形请求；没有声明容量时不虚构型号窗口值。

## 验证

- 新增 26 项后端测试：归档顺序/失败、取消、源状态变化、保护提示词、两种工具协议配对、容量拒绝、无损模式、配置及路由能力交集、网关与直连一致性、缓存分母与重复观测。
- 六家型号的可缓存请求对照：加入不收紧实际请求的能力元数据后，发送字节、缓存标记和缓存指纹一致。
- 真实 Agent 循环的本地模型替身：容量触发一次归档压缩，后续两轮保持完整前缀追加，只标记首个重建请求。
- 内核 unittest：318 项，全部通过（其中 1 项按既有条件跳过）；框架自检 595/595；GUI 前缀缓存回归 2/2；代码预算与 whitespace 检查通过。

本轮没有新增付费模型调用，也没有改用户凭据或实际部署配置。以上验证证明本地请求兼容和失败路径行为，不证明生产环境长期缓存命中率已经提高。完整 VERA 终答复核、模型生成式摘要和动态学习厂家参数不在本轮实现范围。
