# 主控 + 专家 A/B 实测（2026-11-23）

脚本：`scripts/verify_specialists_ab.py --live --runs 2`。原始数据：
[specialists-ab-results.json](specialists-ab-results.json)，包含每次运行的回答、工具序列和分模型用量。

## 设置

- 主控：`deepseek-v4-pro`。专家：retrieval 和 coding 都用 `deepseek-flash`。
- 成本按 `keystone/pricing.py` 的目录价计算（CNY，计入缓存命中折扣）。
- 三组，每组每题各跑 2 次，每次都用全新的工作区和 home：
  - `brain`：今天的运行时，主控也可以自己用普通 `spawn_subagent`。
  - `specialists-prefer`：开启专家路由，`delegation=prefer`，只靠请求尾部的委派指引。
  - `specialists-require`：`delegation=require`，检索和改代码的工具只给专家，主控只保留 `spawn_subagent`/`catalog_expand` 等控制类工具。
- 三道题都是本地题，判分是确定性的：
  - research：在 7 份 docs 中回答 4 个事实，其中有过时的 FAQ 和被否决的会议纪要作干扰；至少要引用 2 个正确文件。
  - coding：修好 cart 模块的 3 个 bug，用它自带的测试判分。
  - mixed：在两份长文档（规范 §7.3 和后来的决策记录）里找出舍入规则，实现 `round_total`，用智能体看不到的隐藏测试判分。
- 判分修订：research 判分器原来有一条“标题行必须出现 7”的规则。它把正确答案判成了失败：标题只是引导语，或者正文提到了“FAQ 写的是 5”。
  这条已改为“不得断言当前值是 5 或 9”，并用 `--regrade` 对所有组的已存回答统一重判。人工逐条看过，research 的 6 个“通过”都是正确答案。

## 结论

1. **只靠提示，主控不会委派。** `prefer` 组 6 次运行一次都没调用专家，`routes=[]`。冒烟时 `advise` 也一样。
   它和 `brain` 的差别都在噪声范围内。所以 advise/prefer 两档相当于没有这个功能。
2. **结构性委派（`require`）在检索类任务上效果很明显。** research 题主控输入降了 85%（10.8 万 → 1.6 万），
   成本降了 71%，耗时持平，正确率不变。主控每次只看目录，只展开 1–2 条，回答里带着条目 id 和 path:行。
3. **小型编码任务不值得交给专家。** coding 题两组都通过，但 `require` 成本高 45%，耗时是 3.2 倍，请求数是 4 倍。
   flash 专家比主控自己改要多走很多步，每次 handoff 还有固定开销。
4. **检索加改代码的混合任务：更便宜也更稳，但更慢。** mixed 题 `require` 2/2 通过，`brain` 1/2，`prefer` 0/2。
   失败都出在同一处：漏掉了决策记录里“CHF 只对现金按 0.05 舍入”这条修订。`require` 的成本低 42%，但耗时翻倍，
   因为专家串行执行，再加上主控的核对。
5. 样本很小（每格 n=2），只测了一个厂商族，题目也是本地题，所以正确率的差异不能算显著；成本和 token 的差异则方向一致、幅度很大。

## 决定

- **保持 opt-in**：`specialists.enabled` 默认 `false`，`delegation` 默认 `advise`，行为与今天完全一致。
- 如果要启用，建议只对**检索为主**的场景开 `retrieval` 专家并设 `delegation=require`，这是唯一有明确收益的组合。
  coding 专家先不要给小任务用。`require` 会把检索工具从主控手里拿走（主控看不了文件，只能展开目录），
  这个代价要按场景权衡。
- 后续值得做（本次没做）：让检索专家并行执行；在路由层按任务规模决定要不要委派，小任务留给主控；换其他厂商组合复测；把 n 提高到 5 以上。
